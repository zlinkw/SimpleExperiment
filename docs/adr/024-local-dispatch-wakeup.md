# 本机调度、按配额手动排队与退出唤醒

所有新提交和旧 server_prequeue PLAN 的未派发 job 默认由本机调度。历史已在服务器的任务保留原身份及执行位置，旧调度配置不再自动把剩余任务塞进服务器队列。

运行进度提供单 PLAN 和全部剩余 job 的入服务器队列按钮。每次点击固定当时尚未派发的集合；按每台服务器每张卡的 job 配额分配，包含同机逐卡配置。1 和 6 的配额在 7 个任务的整数倍上精确分为 1:6，其余采用最大余数法稳定取整。忽略当时忙闲状态计算排队比例，实际启动仍服从显存、逐卡并发和服务器占卡上限。后续新增 job 继续留在本机。

按钮共用已有手动派发、源码验证及产物审核入口，永久删除保持双确认和精确路径保护。只有审核完成且项目、连接、配额、停止意图和原任务身份均未变化，才一次写入全部 ready 意图及稳定 commandId。已绑定、运行、未知、召回中或停止中的任务不进入批次。发送回执未知时保留原身份，禁止自动重发。

CLI 对应 `simpleex task dispatch --remaining --workflow ID --confirm` 和 `simpleex task dispatch --remaining --all --confirm`。API 使用 `tasks.dispatch`，`distribution=quota_remaining`，明确 workflowId/workflowIds 或 all。旧的精确 GPU 手动派发入口保留。

本机调度每 500 ms 主动查询；协议 2 调度只等待当前 tmux 执行库存，产物和日志在既有进度查询中独立核实。本轮主动查询发现本项目精确 commandId 的窗口退出时，立即唤醒调度；若已有轮次未结束，合并成结束后的一个立即轮次，禁止重叠派发。GPU 仍按该轮主动读数和配额判断；释放执行资源不代表产物确认完成，也不重跑原任务。

调度 GPU 查询最多等待本轮 350 ms，已返回服务器先参与派发。慢服务器的在途请求继续合并，不阻挡其他服务器，也不作为空卡证据；晚到结果只供下一轮消费一次，本机接收超过一秒或连接代次改变即丢弃重查，避免每轮重新发起使慢服务器永远无法参与。普通手动刷新仍等待完整查询。

慢产物、源码范围查询此前使用与窗口库存相同的两个紧急请求名额，并发时窗口请求尚未开始便被调用方八秒限时取消。产物及源码查询改走普通控制通道，紧急通道保留轻量执行查询及停止。相同只读 POST 在传输层合并在途请求，调用方分别持有取消订阅；已完成值不缓存为当前事实，写操作不合并或重试。提交前执行查询的调用方等待上限调整为 30 秒，失败仍显示未核实并停止本次提交。

回归覆盖真实 Host 轮次、任务退出但产物未确认、轮次间唤醒、停止优先、全部配额空位填充、单机及跨机比例、未知 GPU、取消审核、配额和任务变化、持久事务同对象跳过写入、重复点击、渲染脚本按钮载荷、CLI、独立订阅取消及慢产物请求隔离。真实用户 PLAN 与远端部署不属于本次自动验证范围。
