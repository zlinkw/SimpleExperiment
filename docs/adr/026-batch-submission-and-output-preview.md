# 批量提交与产物预览等待

## 依据

2026-10-19 对已重载的 0.5.392 读取本机 discovery、capabilities、状态、操作列表和面板诊断，未触发运行、同步或删除。三个同时提交的 PLAN 都选择 jqg_zlk 校验，其中一个服务端校验耗时 67730 ms。另一个原校验已完成，父提交仍显示待确认。historyChoiceMs 包含用户操作时间，不能全部归为后端耗时。

面板诊断在一分钟内记录 206 次完整状态发送，约 142 MB；这是本机 Extension Host 到 webview 的 IPC，不能当作隧道吞吐。端点未报告限流拒绝，最近一条队列等待约 91 ms；没有做链路带宽测试，不能据此断言带宽充足或耗尽。

代码显示，批次每四个 PLAN 固定成组，组末等待派发查询；并发校验又按同一空卡排名选中相同 Worker。Agent 的原操作查询在事件日志追加后重新解析全部历史；热校验在 HTTP 接收线程同步核对源码元数据。重跑产物预览则逐个 job、逐个节点串行等待。

快速文件索引覆盖目录浏览、同步清单和内容缓存，并不自动消除上述调度、操作日志、IPC 和清理预检成本。confirmed_paths 清理采用当前文件系统元数据指纹，不能用浏览索引或旧完成状态授权删除；后端不为这条路径重复哈希全部大型权重。

## 变更

- 批量校验在健康候选 Worker 间均衡分配，保留同 PLAN 的稳定选择；这不绑定正式 job 的 GPU 或服务器。四条提交通道滚动前进，后台空卡派发不阻塞其他授权提交。待确认的原校验不再被批处理覆盖为失败，也不重放提交。
- 原操作状态与派发使用有界独立通道，停止/执行核对、日志、目录与传输仍分别限流。普通并发配置保持不变。完整 UI 状态合并间隔改为一秒，按钮回执仍即时发送。
- Agent 首次读取操作日志后只解析完整追加行，部分行等待后续完成，截断/轮换重建；并发读取共享解析锁。热/冷校验均先接受原异步操作，再核对源码和当前产物；结构缓存的原有新鲜度检查保留。实际完成的源码元数据计数提供进度，不能用心跳伪装校验进展。
- 重跑预览最多并行两个 job，节点只读指纹预览并行，结果按原输入顺序归并；任一预览失败不进入确认或执行。展示实际节点预检进度。实际删除不并行，不减少预检。
- 生产运行确认恢复为 VS Code 原生 modal，完整展示每个服务器、类型、路径，两次确认。并发弹窗排队；取消不批准，旧面板回复不能批准原生请求。保留原面板入口兼容，生产 Host 使用原生弹窗。

## 边界与验收

不执行现场删除、训练、同步或远端 Agent 更新；本机回归不能冒充现场端到端提速。原生 modal 通过生产方法与 VS Code API 替身验证完整长路径及两个阶段，不弹出真实删除确认。Agent 端优化需部署新 runtime 后生效，本机提交、请求调度和原生确认需重载扩展后生效。

测试覆盖滚动提交、均衡校验、未知结果保留、控制通道隔离、日志追加/半行/轮换、并行只读预览和失败阻断、原生双确认与旧回复隔离；打包门禁继续覆盖新鲜产物、PLAN 源码、删除安全、索引增量、生成面板脚本和运行闭包。
