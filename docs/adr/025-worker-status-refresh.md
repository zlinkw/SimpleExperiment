# Worker 状态刷新与产物重试

## 问题与现场依据

2026-10-19 在运行中的 0.5.391 通过当前 SimpleExperiment discovery、capabilities 和只读 API 采样。四台 Worker 心跳持续，重连次数为 0；初次采样队列等待为 0–1 ms、限流拒绝为 0。每台每分钟约 200–450 个请求，说明查询频率偏高，但不能据此认定隧道带宽耗尽。状态、操作列表、任务列表和 GPU 本机 API 分别约 53、83、793、72 ms；这些是插件 API 响应时间，不能冒充端到端网络吞吐测试。

同一次 operations.list 中，edrl 原 validate-plan 已完成，父 plan-submit 仍失败；summation 本机原操作仍为 stalled，同时对应 Worker 的 operation_completed 已包含“计划校验通过”。因此两个截图的直接原因是结果归并和恢复入口漏查，不是实际校验失败。未做大流量测速，无法排除其他时段的链路拥塞。

## 修复

- 原刷新统计来自已退役的 schedulerStates，Worker 任务存在时也显示 0。协议 2 刷新直接主动查询已启用 Worker 的任务、GPU 和原 operationId，分别报告实际数量和未知项；产物慢查询不阻止执行库存更新。
- 60 秒未返回不再制造失败终态。前台等待无进展只结束本轮等待，不发送 stop/cancel；明确停止仍走用户操作。后台轮询退避，前台等待期间撤去同一操作的后台计时器。
- 旧超时 stalled 操作允许按原 Worker/operationId 重新读取。中断提交卡仅绑定原校验；旧卡缺少绑定时只采用同 PLAN、相近时间内唯一原校验。恢复只解释校验结果并提供继续提交，绝不将校验成功当成训练已派发，也不自动重放下一阶段。新提交保存精确父子操作绑定。
- 已完成 job 与 PLAN 增加独立的刷新产物状态、重试产物同步。单 job 请求冻结 planId/index/commandId；PLAN 只处理已完成 job，不读取运行中同组任务的可变产物。保留当前勾选范围、同步暂停、删除保护、精确路径和来源核对。
- 手动核对绕过旧同步回执和重试冷却，但仍复用索引与内容哈希，只复制变化文件。只读刷新不传输；丢失传输回执不重放写请求，下一次先主动查验实际内容。重复点击合并到同一在途请求。
- FILE_INDEX_INVALIDATED_DURING_READ 仅对 sync.projectInventory 的当前连接只读请求最多重读三次。切换项目、连接、取消或其他错误立即结束，未知不等于缺失；不重试破坏性操作。

## 后续优化顺序

1. 分别记录等候队列、网络响应、服务端执行、索引和 UI 归并耗时；目前的 queueWaitMsLast 只是最近一条，不是尾延迟分位数。
2. GPU/执行库存保留轻量优先通道；日志按可见 job 拉取，产物只检查新增或变化文件。一个 job 完成只触发它自己的产物核实与增量同步。
3. 收敛同一 Worker 的相同查询，待确认操作采用退避；不以每次全量校验换取表面实时。
4. 只有持续观测到请求在队列等待而服务端和链路仍有余量时，才调整并发；持续带宽接近上限时才评估隧道或文件传输带宽。保留现有每 Worker 4、全局 8 的普通请求并发，不据单个超时报错调高。

只读现场样本保存在本机独立验收目录，不进入源码、VSIX 或科研结果。未主动重跑、停止、清理训练任务，也未自动部署远端 Agent。
