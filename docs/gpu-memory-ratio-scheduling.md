# 按显存比例共享显卡

## 设置

常用设置只需填写“每个 job 按多少 G 显存计算”，默认 24。例如 24G 显卡一个 job、48G 两个、96G 四个。每台服务器不填时使用统一设置；需要单独设置才填写。连接服务器后，页面直接显示按已保存设置计算的每张卡 job 数量。

原有其他参数仍可在默认折叠的“高级调度选项（一般不用修改）”中调整，不必填写。单卡数量预览复用实际调度计算，也显示旧高级设置的影响；服务器没有当前显卡信息时提示等待连接，不猜测数量。预览是设置说明，不触发查询、预约或派发。

VS Code 设置键及高级参数如下；Worker 覆盖项不填则使用统一设置，已有值继续保留。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| gpuMemoryRatioEnabled | true | 开启按显存比例计算自动任务上限；关闭时一卡一个自动任务 |
| gpuMemoryPerJobGb | 24 | 每任务显存基准，单位 GiB |
| gpuMemoryMaxJobsPerGpu | 0 | 单卡自动任务额外上限；0 表示只按比例 |
| gpuMemoryReserveGb | 0 | 准入新任务时额外保留的显存，单位 GiB |
| gpuMemoryTolerancePercent | 3 | 容量报告误差允许值，范围 0～5% |

设置键前缀为 `simpleExperiment.scheduler.`。Worker 覆盖项写入既有 Worker 配置，不新增服务器状态文件。显式 false、0 与留空继承互相区分。参数用于新派发；已经由服务器接收的任务继续使用其原有选项。

## 调度规则

统一使用现有 GPU 遥测中的 MiB 数值，GiB 按 1024 MiB 换算。单卡上限是总显存除以每任务基准并向下取整，最低 1；允许小幅报告误差，再应用用户设置的额外上限。默认 24/48/80/96 GiB 分别对应 1/2/3/4 个自动任务。

新开一张卡继续遵守原空卡阈值。已有本项目实际自动任务的卡，可以在实时空闲显存足够时继续接收任务，不再要求其利用率回到空卡水平。每个新任务需有一份经容量误差修正的基准空闲显存及用户保留余量；同次准入循环扣除刚批准的显存份额。跨轮询也按已准入数量保留基准份额，避免尚未分配显存的任务挤占用户设置的保留余量。

已派发且尚未观察到实际分配显存的任务也计入数量。远端 Scheduler 根据实际 tmux 窗口的 admitted、starting、running 阶段重新统计，忽略已退出窗口；重启从这些窗口重建，不读取旧任务状态 JSON。每轮使用现有 Scheduler 准入互斥，同卡并发不创建第二套调度器。

本机按显存份额生成重复 GPU 槽位，预派发按份额计算服务器权重。既有 maxConcurrentGpus 继续限制同时使用的物理卡数量，不把同一卡的四个任务误算成四张卡。手动派发继续指定原 GPU，绕过自动上限与资源等待；其实际显存仍反映在 GPU 遥测中。

没有可靠总显存数据或旧 Worker 不支持新协议时，保留单卡单任务规则。显存比例是准入估计，不是进程显存硬隔离，不能保证消除所有 OOM；不修改项目 batch size、模型、环境或科研规则。

## 远端版本

Agent 和独立 tmux Scheduler 均需支持 gpuMemoryRatioScheduling=1。客户端同时核对 Agent 能力与实际 Scheduler 查询能力，不能把新磁盘文件版本冒充运行版本。旧控制进程继续按原单任务规则运行；新共享请求不能借旧进程静默丢弃参数。

“准备 Agent”或重新部署会一起更新 Agent 与独立 Scheduler。Agent 启动时核对当前项目控制窗口中的运行版本和两份 runtime 来源哈希；需要更新时仅替换已核实的控制 pane，保留原窗口、取消围栏、已接收命令以及所有运行/排队任务窗口。新版控制进程直接从这些窗口恢复队列，不读取历史任务文件、不重复提交。

即使 Agent 已是最新版、上传被跳过，部署入口仍主动查询控制进程；发现旧 Scheduler 时自动重启 Agent，由其启动流程完成控制进程更新。用户无需手动关闭窗口。归属不明、控制窗口结构变化或重启未核实时明确报错，不扩大到关闭会话、科研窗口或 PID。缺少运行证据不能宣称更新成功，磁盘文件版本也不能替代控制窗口内的实际运行证据。

更新保留已接收任务的原调度参数；新提交使用当前设置。开发验证只使用隔离 tmux 和轻量 CPU 任务，不自动部署生产服务器。
