# 0.5.328 PLAN 清理范围与审核性能

## 修复

PLAN 清理只处理当前 PLAN 的独占配置及声明目录中的关联产物。PLAN 文件、默认或基础配置、被其他 PLAN 引用的配置及共享资产保留。配置继承关系参与判断，不能只因为某个默认配置仅被当前 PLAN 直接引用，就把它当作独占配置。

此前 `confirmed_paths` 分支会清除候选上的所有保护理由，导致共享配置也进入删除候选。现在把 PLAN 清理范围保护与产物归属提示分开，按完整路径确认不能覆盖前者。API 显式传入路径也必须属于同一 PLAN 的可处理范围；独立文件树和 SimpleSFTP 文件接口的原有路径删除规则不变。确认及开始执行前重新读取本机配置引用图，配置变化或被新 PLAN 引用时要求重新审核，不执行删除。

清单读取此前按节点、声明逐项串行执行，并混入所有历史运行路径。现在优先使用当前 Worker 展开的声明，只有当前声明不可取得时才把旧路径用作查询定位；按实际节点和输出目录去重，并限制最多四项并行只读查询。仍只读取声明输出目录内的有限清单文件，不扫描所有历史目录或大型权重。不存在的输出不进入可处理列表；禁用的 Worker 不加入清理目标。

切换移走/删除或“先处理可连接服务器”时，复用本页内存中的路径发现结果，不重新调用 PLAN 展开和清单发现。仍按所选方式进行实际文件预检；确认和执行时继续核对真实文件及节点。切换后原确认失效，删除仍须对同批完整路径确认两次。显式“审核文件”仍会刷新实际发现；已开始执行的批次不能通过切换模式重发。没有新增持久化文件索引或远端状态文件。

## 验证与交付

本轮用户新提交的 `comparison/aoept.yaml` 六个 job 均停在“待核实”。只读 API 状态记录六次 `TMUX_QUERY_FAILED: can't find window: simple-sch-…`；实际 tmux 清单已有配置前缀 `zlk-sch-…`，没有这些 job 的任务窗口。新增真实隔离 tmux 回归：先以旧前缀创建共享 tmux 服务，再用当前前缀启动 Scheduler，旧实现稳定复现同类错误。根因是 tmux 子进程继承服务最初的环境，而非当前 Agent 的环境，Scheduler 内部创建任务时由此定位错误会话。

Scheduler 新建和升级重启现在显式传入配置前缀；任务新窗口使用当前控制器所属的原生 sessionId，GPU 会话匹配也使用精确目标，避免名称相近或旧环境导致误定位。Agent 和清理入口已核对使用本轮配置前缀，不以修改共享 tmux 全局环境修补，不关闭其他用户窗口。保留旧控制器的只读兼容定位，不按旧名字新建会话；本轮没有自动重发这六个 commandId，也没有代用户重新训练。

先用旧构建重现默认配置进入删除候选、切换模式重复清单读取两项失败，再验证修复。回归覆盖保留 PLAN/默认配置、继承/跨 PLAN 引用、确认前新增共享引用、API 越界范围、模式往返、旧确认失效、输出去重、并行上限、真实缺失目录和已有清理/覆盖/恢复流程。真实隔离 tmux 验证旧服务环境与配置前缀不同时仍能启动任务；Scheduler 升级保留已有执行/排队窗口，新 H20 任务仍能同卡六 job 并行。

发行、完整验证及安装结果将在核实后填写。SimpleSFTP 沿用 0.2.90，无协议变化。
