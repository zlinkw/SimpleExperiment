# 同步页面删除与刷新

批量删除、单位置删除、全部 Worker 副本删除及已确认同步覆盖清理共用 `SyncScopeDelete`。这些入口不再调用通用 `sync.deletePath`，不查询或取消历史传输，不以旧传输记录判定文件占用或删除完成。

两次完整路径确认保持不变。SimpleSFTP 的现有 `confirmed_paths` 协议核实根目录、固定类型、链接和直接父目录；清理只操作该父目录内的直接子项。删除由受管 tmux 窗口执行，插件主动查询窗口和文件系统。请求响应丢失后只查询，不重发删除；文件实际不存在且执行器已结束才能完成。当前执行器仍存在时本轮等待有界，不创建第二个执行器。查询失败可刷新，不能当作空目录或成功。

完成、部分失败和异常都重新读取尝试处理路径的父目录。旧查询响应及错误失效，旧等待标志释放；根据新的目录清单移除文件树、异常筛选和临时勾选项。已不存在的路径不建立墓碑。单文件删除保持其他目录的展开位置。文件树错误写入扩展宿主日志，部分失败的具体原因不会被后台刷新覆盖。

2026-10-14 只读核查 0.5.312：jqg_zlk 的 `work_dirs` 有 0 项，nwpu3、nwpu2 各 26 项，nwpu5 有 25 项。用户再次删除失败原因是旧通用传输入口按同一服务器根匹配未结束的旧请求，再调用不支持该删除协议的回执恢复；并非所有目录均已删除。未执行真实删除、清空历史记录或远端部署。

回归：`syncScopeDelete.test.js` 验证丢失执行响应、主动核实、执行器防重、空目标和未知状态；`syncScopeDeletionRefresh.test.js` 验证真实调用链与部分失败后刷新及过期响应；`syncScopeTransferBatch.test.js` 和 `syncScopeTree.test.js` 保留同步范围、批次和展开行为回归。配套 SimpleSFTP 0.2.85 的已发布删除协议可复用，无需修改服务器配置。

完整构建首次暴露既有 `manualTmuxAdmission` 夹具的时间竞争：手动任务固定等待 1.2 秒，自动任务准入时已自然退出，使并发断言失败。夹具改用有界释放信号维持手动探针，断言通过后才允许其完成；外层进程继续限制 10 秒。生产调度代码未改。

## 0.5.314 / SimpleSFTP 0.2.86

0.5.313 的实机删除仍在预览中逐字读取权重做 SHA256；只读复现中存在性查询约 0.5 秒，预览超过 50 秒未返回。清理方法又未接入进度通道，被客户端当作 30 秒静默控制请求取消。这不是旧传输记录再次阻断。

按已确认路径删除仅枚举本次真实目录的类型、设备、inode、大小及纳秒修改/变更时间，生成本次元数据指纹，不读取权重内容或科研清单。删除前继续复核完整子项清单、类型、链接、硬链接、挂载、安全根及物理直接父目录；变化须重新确认。普通移动和恢复仍保留内容哈希。按路径永久删除不再额外写服务器审计清单；受管执行器的固定输入只用于这次操作，不用于证明文件存在。新客户端先核对配套能力，避免旧 SimpleSFTP 再进入全内容扫描。

清理真实扫描进度通过本次请求的内存通道返回，阶段错误明确包含接口名；查询仍有界，查询失败不代表已删除。代码同步走现有 SimpleSFTP API，并显示实际进度。上传开始前通过一条只读 SSH 通道建立所选文件基线，实时统计远端已写入字节、已写满文件数及本次总字节/文件数；旧副本不算本次已传输，大小相同不算内容核验成功。不保存进度文件，不用整棵历史文件树计算进度。

实际传输没有固定总时长或 120 秒自动取消。未观察到新增数据时提示等待；恢复写入后继续显示实际数据，用户仍可取消。只读进度查询本身失败时显示查询不可用，数据流和最终 SHA256 核验继续独立处理。删除查询与执行状态依然由实时文件和 tmux 核实。
