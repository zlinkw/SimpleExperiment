# 运行卡片状态交替修复

## 原因

0.5.322 中，当前任务失败后会退出结果查询选择；服务端在查询其他任务时又过滤未选中的已退出窗口。本机因而先读到失败，再读到“未发现”，下一轮重新加入查询后又读到失败。通过当前插件只读 API 连续六次采样复现了这种交替，正常运行任务没有相同交替。

提交预检的临时清单与持续进度查询还共用一份显示结果；查询错误和原生 observation 变化没有完整参与显示失效条件，缓存也没有按查询有效期退出。

## 修改

- 当前逻辑 job 的失败和完成结果继续主动核对，不补齐缺少身份的历史记录，不查询被新运行替代的旧结果。
- 实际 tmux 窗口清单包含已退出窗口，结果选择只补查不在窗口清单中的声明产物，不能把真实窗口过滤掉。
- 临时提交预检只返回给该提交，不覆盖运行卡片使用的结果；失败时同样不覆盖。
- 查询失败、恢复、协议及原生执行/结果变化刷新显示。缓存到期后重新计算未知状态；时间戳变化本身不触发结构重建。未知不等于失败，也不自动重复派发。
- 不新增服务器状态文件，不以本机旧失败记录替代查询，不启动、停止或重跑现有任务。

## 验证

新增 taskProgressStability 单文件回归先复现五项失败，再验证修复，覆盖真实 Python 查询函数、Host 查询发布及投影、结果选择和缓存有效期。Python 仅提取相关函数，以合成 tmux 行测试，不导入完整 runtime。

额外的旧 serverAuthoritativeProgress.test.js 在当前源码与基线 429cbad0 的 Host 源码下均为 5 通过、7 失败，涉及旧协议夹具与缺少 cleanupDigest 的抽取环境；未计为通过，也未为此恢复旧回执逻辑。现行单文件回归、完整打包门禁及真实隔离 tmux 另外执行。

## 项目命令错误的边界

本轮通过插件主动查询取得的失败窗口中，有项目测试入口报告“模型类别维度与 label_schema 不一致”。该错误来自项目测试代码对配置类别数与预处理 label_schema 类别数的检查，不是卡片刷新产生，也不能仅凭这条错误认定原始数据损坏。未自动改动项目类别配置、标签、权重、环境或重新运行任务。另一条 nvJitLink 优先使用环境库的文本属于提示，不是该 ValueError 的原因。
