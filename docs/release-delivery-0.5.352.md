# 0.5.352 单卡配额与总剩余显存

## 用户规则与现场

用户明确要求自动识别服务器全部物理 GPU，仅配置每卡最大并行 job 数及该卡可派发所需的最低总剩余显存。门槛确认为 22 GiB，含边界；它不是每个 job 的预估用量。H20 保留此前每卡最多 6 个，本机其他服务器默认每卡 1 个。现有科研任务不停止、不删除、不重跑，不修改环境。

2026-10-16 本地 API 为 0.5.351，H20 GPU 0、1 各有其他用户的 VLLM 进程，已用 108765 MiB、总量 143771 MiB，剩余约 34.2 GiB。旧版不仅检查显存比例，还要求空卡或已有本插件任务，因此这两张卡被排除，虽然剩余显存超过 22 GiB。GPU 2 当时运行本项目三个 job。当前 H20 配置是旧比例 24 GiB、物理卡上限 3，旧单卡额外上限为 0，正常旧比例预览为每卡 6。

## 实现

- 新参数为 gpuJobsPerCard 和 gpuMinFreeMemoryGb，支持全局默认与每 Worker 覆盖，默认 1 和 22。UI 仅显示这两个 GPU 调度参数和真实卡数/余量。物理卡数自动读取实时遥测，旧 maxConcurrentGpus 不再限制新规则。
- Host 分配、手动派发请求、Worker 可用性、独立 Scheduler 的本机/服务器排队准入都使用同一配额与总余量规则。利用率、已用显存阈值、其他进程存在与否、每 job 显存比例、估算保留量均不作为新任务准入条件。未知显存不能当成满足门槛。
- 并行数以实际 admitted/starting/running 窗口计数，包含手动任务；排队不算正在并行。手动目标仍固定到用户指定卡，但同样遵守该卡配额与总余量。自动任务优先原卡，其他实际可用卡也可接收。
- 新显式配额优先。旧比例只在首次未配置新参数时转换为兼容配额；H20 转为 6。保存后清空新参数会回到全局继承，不复活旧比例。旧字段保留为弃用兼容输入，原算术 helper 仅供迁移及历史显式入口测试。
- 配置通过受限 configure-gpu-quota 控制更新 Scheduler 原生窗口属性，修改已接收队列的准入策略，不创建、召回、停止或重放 job。重启从真实窗口与策略属性重建，无新增状态文件。更新 Agent/Scheduler 仍由用户通过原入口执行；不自动部署。
- 旧 Agent 不具备 gpuQuotaScheduling=1 时，插件拒绝按新规则启动，不静默退回旧准入。

## 验证与边界

新增原生 Python 函数提取测试：其他用户进程及 100% 利用率不阻断余量充足的卡，22 GiB 边界可派发，21 GiB/未知不可派发，每卡 6 个上限与手动绑定生效。实际本机 allocator 在三张已被外部进程使用但余量满足的卡上分配每卡最多 6 个；实际 Host RPC 仅携带新配额与余量。覆盖参数保存、清空继承、迁移、渲染表单、策略更新去重和既有隔离 tmux 队列不增删任务的配置往返。

额外抽查旧 idleGpuDispatchLifecycle.integration.test.js，未修改 HEAD 源码复现 19 项中 17 项基线失败（旧协议夹具及未注入的已有模块）；旧 distributedQueueStartup.test.js 也在 HEAD 原始源码/编译模块上复现 20 项中 11 项基线失败。这两个文件不属于当前发布门禁，未借新机制改写它们。日志保留在系统临时目录 simpleex-quota-baseline.log 和 simpleex-quota-startup-baseline.log。当前原生协议通过独立配额、真实 Host 调用、HTTP 配置分支和隔离 tmux 回归验证。现行门禁夹具补齐真实显存总量和新协议能力，没有放宽生产准入来兼容缺失的遥测。

配置更新按 Worker 串行，旧请求不覆盖新设置；降配额只阻止后续启动，不终止现有任务。隔离 tmux 测试已验证手动与自动共同遵守同一卡配额、精确停止只释放一个名额、Scheduler 更新保留已有窗口及队列，再由新显式配额启动每卡 6 个合成 CPU job。
