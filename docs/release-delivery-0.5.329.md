# 0.5.329 本机等待任务的跨 Worker 派发

## 证据与原因

用户报告本机仍有排队任务、其他服务器有空卡，却继续等待单个 Worker。通过 SimpleExperiment 0.5.328 的 `state` 和 `tasks.list` 只读查询，所选 `comparison/aoept.yaml` 实际已有四项运行、两项在 NWPU3 的真实 Scheduler/tmux 窗口排队；H20 三卡空闲。NWPU5 的第二张卡也空闲，但其用户配置的并发占卡上限为一，不能把该卡当成额外自动名额。四台 Worker 已同步并运行 0.5.328。

新增跨轮次回归复现：先就绪 Worker 接收三个任务；客户端按新生命周期规则把启动响应视为传输结果，将任务显示为待核实；如果查询发生在窗口创建之前，旧容量归并便丢失已发请求的名额。同一 Worker 看起来又有三个空位，后续任务提前进入其服务器队列，稍晚就绪的 H20 因此拿不到剩余本机任务。

## 修复边界

本机分配时保留原 commandId、Worker 和 GPU 的未核实启动输入。传输响应、一次未发现窗口或查询失败均不提前释放名额。此输入仅用于避免重复分配，不证明任务已运行，不替代 Scheduler、tmux 或产物查询。首次查询取得对应实际窗口后，名额交由实时执行证据；主动查询确认取消或完整结果后释放。历史 unknown 状态或属于其他 commandId 的旧输入不占名额；确认未发送及明确准入拒绝路径也清除本机启动输入。

因此，先就绪 Worker 只接收其当时可用的自动名额，剩余未派任务留在本机；其他 Worker 就绪后按当前 GPU、显存比例、代码版本和用户上限参与同一次分配。保留手动同卡并发、服务器预排队和既定安全边界，不把“待核实”显示成“运行中”。

本轮没有调用生产停止、召回、重新派发或训练接口。已被服务器接收的两个队列窗口没有自动搬走，当前运行任务不受影响。修复防止后续本机任务过量预派；已有远端排队可由用户沿用“召回本机”或“手动派发”入口调整，必须先主动核实原 Worker 释放。
