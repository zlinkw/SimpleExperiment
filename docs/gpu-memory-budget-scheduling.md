# 滚动显存观察与整批调度

目标是缩短整批任务的结束时间。显存占用率不是速度保证，本功能不宣称已经获得加速结果。

## 自动观察

插件不要求消费项目新增回调，不导入 torch，不猜测日志中的 Epoch 是否表示完成。每个项目、PLAN 身份与 revision、代码来源、case、执行模式、Worker 和 GPU 型号及容量组合形成独立观察组。不同 seed 共享本组已经观察到的最大值。模型、batch size、输入尺寸或精度不同的任务必须属于不同 case 或 PLAN revision；插件无法从任意项目的动态代码证明这些配置相同。

未知组合首次只启动一个正式 job，并独占插件在该卡上的派发预算。其他组合可同时在其他空卡观察。确认实际 GPU 分配后开始计时，默认需要连续 600 秒有效观察，相邻有效观察间隔超过 30 秒就重新计算连续覆盖时间，已有峰值仍保留。项目无须输出特定日志。正常任务提前退出且已有实际显存采样，也可形成观察值。没有实际分配或身份无法核对时，不把等待时间算成测量。

优先使用现有设备采集器中精确 commandId、projectId 标注的 GPU 进程显存。独占观察同时纳入相对启动基线的整卡增长。无法归属到进程时，只在单任务观察中使用整卡占用的保守上界；共享派发时不抵扣无法归属的已用显存。

## 显存预留

预算为本组最大已观察峰值乘 1.2，再加 1024 MiB，向上取整。该余量是保守策略参数，不是经过本项目实验验证的 OOM 保证。后续阶段的更大峰值继续上调本组预算。

若放大后的共享预算超过空卡余量，但已测峰值加 1024 MiB 仍可容纳，则允许该 job 独占一张卡，预留全部当前余量，不再向该卡补入任务。避免本来能单独运行的大任务因共享预算放大而永久排队。

派发必须同时通过用户配置的每卡并行上限、逐卡覆盖、Worker 总占卡上限和派发前最低剩余显存阈值。阈值仍表示派发前总剩余显存，不改成派发后的剩余量。

设备当前剩余显存必须覆盖新任务预算，加上所有已派发任务尚未实际申请的预算。只抵扣本轮设备快照中精确归属的实际分配，整卡抵扣总额不超过设备已用量。刚接收、未启动、断线和未知状态不释放预留。独占观察结束后，整卡预留换成已测预算。

本机先把预留与原命令身份一起持久化到既有队列，再发送请求。远端 Scheduler 在自己的互斥区内重新检查、记录原生 tmux 窗口预留并逐个准入；不能仅靠本机快照放行。Scheduler 重启从真实窗口恢复，不重放旧队列文件。新协议不把缺少预算能力的旧 Agent 当作兼容实现。

## 整批安排

不等待全部 PLAN 观察完成，也不设置固定批次结束屏障。默认先考虑剩余工作较多的 PLAN；已有正常完成任务时用其实际耗时更新工作量估计。每组未知配置在同类设备上只观察一个，已有预算任务边观察边运行。

源码后台核实结果必须先被一轮调度采用，再允许按刷新期限重新查询。查询超过本轮短等待窗口时，结果仍供后续调度采用，不能在采用前因刷新期限到期而丢弃。实际发送前继续重新核实冻结源码；源码确有变化仍阻止启动。后台查询进行中只保留派发门禁，不把它显示成源码错误，也不覆盖显存等待或旧产物隔离的原因。

不同 PLAN 可共享显卡。可行放置先利用空卡，再按当前任务数均衡增加共享；相同占用数量时选择放入后剩余预算较小的位置，避免空卡闲置而已用卡过度竞争。未知组合仍在等待时，保留最后一张兼容空卡；全部卡忙时选择占用任务较少的一张不再补入，使其自然空出供下一组观察。不终止、不迁移正在运行的任务。未知组合不可运行、归属或遥测不明时继续保守等待。

正常已完成任务的耗时与并发观察作为后续补入的反馈。观察到共享未带来总处理速度收益时不继续增加共享；不额外启动训练基准，不自动改变 batch size、精度或科研配置。这是在线启发式安排，并非全局最优完工时间证明。

## 异常与边界

原生任务窗口出现明确 CUDA OOM 信息后，暂停该组合在相应 Worker 与同类 GPU 上的新派发，并在队列中保留原任务；不自动重跑或停止其他任务。用户需检查失败任务并通过已有处理入口决定后续操作。

峰值和预留存于既有原生窗口选项及本机队列，无额外任务状态文件。遥测失效、短时峰值漏采、数据相关动态分配、后续阶段变化、外部进程抢占以及硬件共享干扰仍可能造成 OOM。需要显存强隔离时应由用户另行配置支持的硬件或驱动机制。

验证仅覆盖确定性的分配、计时、预留、身份及安全行为，未运行科研实验或 GPU 性能测试。
